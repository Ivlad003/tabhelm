# ACP-міст і chrome.debugger збирають браузерного агента з готових частин

Chrome-розширення з бічною панеллю-чатом, яке керує будь-яким із шести консольних агентів і дозволяє йому діяти на поточній вкладці звичайного Chrome, сьогодні збирається майже повністю з готових open-source блоків, і жоден із них не потрібно писати з нуля. Ключова знахідка: **Agent Client Protocol (ACP)** став спільним знаменником — Gemini CLI, Cursor CLI, OpenCode і, ймовірно, Grok CLI говорять ним нативно, а Claude Code і Codex CLI покриваються офіційними адаптерами `@agentclientprotocol/claude-agent-acp` та `@agentclientprotocol/codex-acp`, тож один ACP-клієнт обслуговує всі шість агентів, а поле `session/new.mcpServers` є уніфікованим способом «підсунути» агенту MCP-сервер з інструментами браузера ([ACP agents](https://agentclientprotocol.com/overview/agents), [ACP session setup](https://agentclientprotocol.com/protocol/session-setup)). Найближчий готовий шаблон — **chrome-acp** (MIT, 191 зірка): розширення ↔ WebSocket ↔ локальний proxy ↔ stdio ↔ ACP-агент, з уже вбудованими MCP-інструментами `browser_tabs`/`browser_read`/`browser_execute` ([Areo-Joe/chrome-acp](https://github.com/Areo-Joe/chrome-acp)); шар керування вкладкою варто брати з **Nanobrowser** (Apache-2.0, 14,1k зірок, `chrome.debugger` через puppeteer-core `ExtensionTransport` і DOM-дерево в стилі browser-use) або з Playwright MCP Bridge / hangwin/mcp-chrome ([Nanobrowser](https://github.com/nanobrowser/nanobrowser), [GitHub API, 2026-10-12](https://github.com/nanobrowser/nanobrowser)). Локальні моделі через Ollama працюють, але лише умовно: 7–9B моделі «здебільшого провалюють» багатокрокові браузерні задачі, прийнятна надійність починається з ~27–32B dense або 30B-A3B MoE на 24 GB VRAM, і будь-яка конфігурація розвалюється без підняття контексту до 32–64K токенів ([localaimaster](https://localaimaster.com/blog/browser-use-ollama-local), [Ollama docs](https://docs.ollama.com/context-length)). Найтонші місця — не моделі, а платформа: 30-секундне життя MV3 service worker, незнімний банер «started debugging this browser», конфлікт із відкритим DevTools, ліміт 1 MB на кадр native messaging і prompt injection, від якої в 2025 році впали всі комерційні агентні браузери ([Chrome SW lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [Brave](https://brave.com/blog/comet-prompt-injection/)).

## Три готові шари покривають 90% розширення

Задачу природно розкласти на три шари — UI в бічній панелі з ACP-клієнтом, локальний host-процес, який запускає агента і виставляє йому MCP-сервер, і шар спостереження/дії на вкладці — і для кожного вже є зрілий open-source код. Таблиця нижче узагальнює кандидатів за даними GitHub REST API станом на 2026-10-12.

**chrome-acp** вартий форку як скелет: його README описує архітектуру «Chrome Extension ↔ WebSocket ↔ Proxy Server ↔ stdin/stdout ↔ ACP Agent», перелік підтримуваних агентів уже включає Claude Code, Codex CLI, OpenCode, Gemini CLI і «any ACP agent», а Bun-монорепозиторій розділено на extension, web PWA client, shared UI і proxy — саме ті пакети, які потрібні ([Areo-Joe/chrome-acp](https://github.com/Areo-Joe/chrome-acp)). Його слабкість — інструменти `browser_read` (DOM як Markdown) і `browser_execute` (довільний JS) занадто грубі для надійного клікання; саме цей шар і треба замінити. Існує ще ранній **acp-sidepanel** (0 зірок, 6 комітів), який показує мінімальний ланцюжок «side panel → `ws://localhost:3000` → stdio-to-ws → claude-agent-acp → Claude Code» ([aganhui/acp-sidepanel](https://github.com/aganhui/acp-sidepanel)), але як кодова база він ще не дозрів.

**Nanobrowser** — найзріліше розширення з усіма потрібними дозволами (`host_permissions: ['<all_urls>']`, `permissions: ['storage','scripting','tabs','activeTab','debugger','unlimitedStorage','webNavigation']`), побудоване на WXT + TypeScript + Vite; `src/background/browser/page.ts` підключається до вкладки через `connect({ transport: await ExtensionTransport.connectTab(this._tabId) })`, а `dom/service.ts` інжектить `window.buildDomTree` у кожен фрейм і повертає `[elementTree, selectorMap]` з `highlightIndex` — тобто саме те представлення сторінки, яке використовує browser-use ([wxt.config.ts](https://raw.githubusercontent.com/nanobrowser/nanobrowser/master/wxt.config.ts), [page.ts](https://raw.githubusercontent.com/nanobrowser/nanobrowser/master/src/background/browser/page.ts), [dom/service.ts](https://raw.githubusercontent.com/nanobrowser/nanobrowser/master/src/background/browser/dom/service.ts)). Важливе застереження: Nanobrowser сам є агентом (Planner + Navigator усередині service worker) і не має MCP; для нашої задачі з нього беруть лише браузерний шар, а цикл агента викидають.

**hangwin/mcp-chrome** — найкраще джерело для native-messaging-половини: розширення з дозволами `nativeMessaging`, `scripting`, `debugger`, `offscreen`, `sidePanel`, host-процес `mcp-chrome-bridge` з Fastify, Streamable HTTP на `http://127.0.0.1:12306/mcp` або STDIO, ref-counted keepalive через offscreen-документ і коментар у `quick-panel/agent-handler.ts`, що «Keepalive is explicitly managed to prevent MV3 Service Worker suspension during streaming» ([README](https://github.com/hangwin/mcp-chrome), [keepalive-manager.ts](https://raw.githubusercontent.com/hangwin/mcp-chrome/master/app/chrome-extension/entrypoints/background/keepalive-manager.ts), [agent-handler.ts](https://raw.githubusercontent.com/hangwin/mcp-chrome/master/app/chrome-extension/entrypoints/background/quick-panel/agent-handler.ts)). Але комітів не було з січня 2026, тож це «кодова шахта», а не upstream, за яким варто слідкувати.

Playwright MCP Bridge і chrome-devtools-mcp — не форк-кандидати, а еталони UX: розширення Playwright при першій взаємодії пропонує вибрати вкладку, кожен клієнт отримує власну tab group, а підключення потребує ручного схвалення або токена `PLAYWRIGHT_MCP_EXTENSION_TOKEN` ([packages/extension README](https://github.com/microsoft/playwright/tree/main/packages/extension)). Варто знати й закриті продукти: Claude in Chrome працює за тією ж схемою (native messaging host `com.anthropic.claude_code_browser_extension.json`), але потребує прямого плану Anthropic, не працює з API-ключем чи `setup-token` і не підтримується у WSL ([Claude Code docs](https://code.claude.com/docs/en/chrome)); Google «auto browse» у Gemini-панелі Chrome доступний лише платним AI Pro/Ultra без API для розробників ([9to5google](https://9to5google.com/2026/01/28/chrome-gemini-auto-browse/)). BrowserOS — відкрита (AGPL-3.0) альтернатива з 53+ MCP-інструментами, але це форк Chromium, а не розширення для звичайного браузера ([BrowserOS](https://github.com/browseros-ai/BrowserOS)).

## ACP робить шість агентів взаємозамінними

Головне архітектурне рішення — не писати шість інтеграцій, а говорити з усіма агентами по ACP. ACP (Zed, серпень 2025) — це JSON-RPC 2.0 через stdio з newline-delimited кадруванням; v1 стабільна, TypeScript SDK `@agentclientprotocol/sdk` 1.0.0 і Rust `agent-client-protocol` 1.0.0 вийшли 25 червня 2026, а v2 — лише Draft від 20 липня 2026 зі змінами у форматі diff і дозволів ([ACP llms-full](https://agentclientprotocol.com/llms-full.txt)). Три протокольні примітиви покривають усе, що потрібно чату: `session/new` з масивом `mcpServers` (stdio обов'язковий, HTTP лише коли агент декларує `mcpCapabilities.http: true`), блокуючий запит `session/request_permission` від агента до клієнта з варіантами `allow_once`/`allow_always`/`reject_once`/`reject_always`, і потік нотифікацій `session/update` типів `agent_message_chunk`, `tool_call`, `tool_call_update` ([ACP session setup](https://agentclientprotocol.com/protocol/session-setup), [ACP tool calls](https://agentclientprotocol.com/protocol/tool-calls)). Саме `session/request_permission` і є тим місцем, де бічна панель показує діалог «агент хоче клікнути Submit — дозволити?».

| Агент | Як керувати програмно | ACP | MCP-інжекція | Дозволи |
|---|---|---|---|---|
| Claude Code | `claude -p --input-format stream-json --output-format stream-json` або Agent SDK з `canUseTool` | Адаптер `@agentclientprotocol/claude-agent-acp` (Apache, 2,6k зірок) | `--mcp-config <json>` + `--strict-mcp-config`; через ACP у `session/new` | `--permission-prompt-tool`, SDK-callback, через ACP `request_permission` |
| Gemini CLI | `gemini -p --output-format stream-json --approval-mode …` | Нативно, `--acp` (0.50+, `--experimental-acp` deprecated) | `settings.json` `mcpServers` або `gemini mcp add`; у `session/new` | ACP; headless має лише `--approval-mode yolo/auto_edit` |
| Cursor CLI | `agent -p --output-format stream-json --force` | Нативно, `agent acp` | `.cursor/mcp.json` (project/user); team-MCP в ACP не підтримується | `allow-once`/`allow-always`/`reject-once`; без відповіді tool блокується |

Кілька нюансів у цій таблиці визначають дизайн. Claude Code не має власного режиму `--acp`; адаптер побудовано на Agent SDK і він підтримує «client MCP servers» і запити дозволів ([claude-code-acp](https://github.com/zed-industries/claude-code-acp)). Вбудовані браузерні інструменти Claude Code (`claude --chrome`) для нашої мети непридатні: вони вимикаються при автентифікації API-ключем і прив'язані до закритого розширення Anthropic, тож **власний MCP-сервер браузера через `--mcp-config` або `session/new` — єдиний переносимий шлях** ([Claude Code docs](https://code.claude.com/docs/en/chrome)). Для Gemini headless-режим `stream-json` одноразовий і не має stdin-каналу дозволів, тому без ACP довелося б працювати в `--approval-mode yolo` — ще один аргумент на користь ACP ([Gemini CLI headless](https://geminicli.com/docs/cli/headless/)). Cursor читає MCP лише з `.cursor/mcp.json`, тому host-процес має записати цей файл у робочу директорію сесії; натомість Cursor — єдиний із шести, хто дає доступ до моделей Grok і водночас має нативний ACP ([Cursor ACP](https://cursor.com/docs/cli/acp), [learncursor.dev](https://www.learncursor.dev/learn/cursor-basics/cursor-models)). Для Codex `codex app-server` — офіційна точка глибокої інтеграції (саме її використовує VS Code-розширення), з транспортами stdio, Unix socket і експериментальним WebSocket ([Codex App Server](https://developers.openai.com/codex/app-server)); `codex-acp` — тонка обгортка над ним. OpenCode найщедріший: `opencode serve --cors <origin>` існує саме для того, щоб сторінка з іншим origin (наприклад, `chrome-extension://…`) могла звертатися до HTTP+SSE API напряму ([OpenCode server](https://opencode.ai/docs/server/)).

Оскільки ACP-транспорт — stdio, а віддалений транспорт (WebSocket/HTTP) ще в роботі у Transports Working Group, створеній 22 квітня 2026 ([ACP llms-full](https://agentclientprotocol.com/llms-full.txt)), розширенню потрібен локальний міст. Готові реалізації: `@rebornix/stdio-to-ws` (використовує ACP UI), `acp-client` 0.6.1 з браузер-безпечним графом модулів і `createWebSocketStream`, proxy із chrome-acp, а для налагодження — `acp-devtools` (прозорий ACP-proxy з web-інспектором) ([acp-ui](https://github.com/formulahendry/acp-ui), [acp-client](https://socket.dev/npm/package/acp-client), [acp-devtools](https://awesome.ecosyste.ms/projects/github.com%2Fmaksugr%2Facp-devtools)).

## Рекомендована архітектура: host володіє політикою, розширення — вкладкою

Збираючи ці блоки, рекомендована схема виглядає так. **Бічна панель** (WXT + React, за зразком Nanobrowser/chrome-acp) показує чат, журнал tool calls і діалоги `request_permission`; вона дізнається активну вкладку через `chrome.tabs.query({active: true, currentWindow: true})`, бо прямого «мій tabId» API в side panel немає, а прив'язка панелі до вкладки робиться через `sidePanel.setOptions({tabId, path, enabled})` ([chrome.sidePanel](https://developer.chrome.com/docs/extensions/reference/api/sidePanel)). **Service worker** тримає один канал до локального host-процесу і виконує браузерні примітиви. **Host-процес** (Node/Bun, встановлюється разом із CLI) робить три речі: запускає обраного агента по ACP як дочірній stdio-процес, виставляє йому власний MCP-сервер з інструментами `snapshot`/`click`/`type`/`navigate`/`screenshot`, які проксіюються назад у розширення, і тримає політику дозволів — allowlist сайтів і перелік незворотних дій. Такий розподіл повторює те, що chrome-acp уже робить із `browser_*` інструментами, і що Claude in Chrome робить через native messaging host ([Areo-Joe/chrome-acp](https://github.com/Areo-Joe/chrome-acp), [Claude Code docs](https://code.claude.com/docs/en/chrome)).

Для транспорту «розширення ↔ host» є два варіанти з різним профілем ризику. **Native Messaging** — «благословенний» шлях: без мережевого слухача, origin фіксується самим Chrome через `allowed_origins` (точні `chrome-extension://<id>/` без wildcard), а відкритий `connectNative`-порт тримає живими і host-процес, і MV3 service worker (Chrome 105+) ([Native Messaging docs](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [SW lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)). Ціна — інсталятор, що пише host-маніфест у три місця (реєстр `HKCU\Software\Google\Chrome\NativeMessagingHosts\…` на Windows, `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/` на macOS, `~/.config/google-chrome/NativeMessagingHosts/` на Linux), 4-байтовий length-prefix на stdio, і головне — **ліміт 1 MB на повідомлення від host до Chrome** (64 MiB у зворотному напрямку), що змушує чанкувати великі a11y-снапшоти і скриншоти ([Native Messaging docs](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)). **Локальний WebSocket** (шлях chrome-acp, page-agent, Playwright Bridge) не потребує інсталяції маніфесту, але відкриває порт, до якого може спробувати підключитися будь-яка web-сторінка: Chrome Local Network Access (стабільна з Chrome 142) гейтить `fetch()`, але «WebSockets, WebTransport, and WebRTC connections to the local network are not yet gated on the LNA permission» ([Chrome LNA blog](https://developer.chrome.com/blog/local-network-access)). Тому WS-сервер має слухати лише `127.0.0.1`, перевіряти заголовок `Origin` проти точного `chrome-extension://<id>` і вимагати per-install токен — DNS rebinding проти локальних сервісів цілком реальний, як показав CVE-2026-33002 у Jenkins ([Rapid7](https://www.rapid7.com/db/vulnerabilities/jenkins-2026-03-18_cve-2026-33002/)). Прагматичний гібрид: Native Messaging для bootstrap (запуск демона, обмін токеном і портом), WebSocket для об'ємного трафіку.

Шар спостереження варто будувати на **фільтрованому a11y-снапшоті з opaque-refs**, а не на сирому DOM чи скриншотах. Playwright-овий `ariaSnapshot.ts` у режимі `'ai'` видає лише видимі елементи, що приймають pointer-події, присвоює refs виду `e12`, кешує їх на елементі, тож незмінені вузли зберігають ref, обходить shadow DOM як звичайних дітей, а iframes робить листовими вузлами з окремими снапшотами ([ariaSnapshot.ts](https://github.com/microsoft/playwright/blob/main/packages/injected/src/ariaSnapshot.ts)). Такий снапшот коштує **~500–5 000 токенів проти 10–50k для скриншота**, а refs дійсні лише для своєї версії снапшота — після навігації чи великих змін DOM потрібен новий ([Playwright MCP README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)). Host повинен прикріплювати до кожного ref епоху снапшота і відхиляти застарілі дії замість мовчазного кліку не туди. Для canvas/WebGL-застосунків дерева немає, і єдиний запасний шлях — режим зі скриншотом і координатами (аналог `--caps=vision` у Playwright MCP). Окремий дешевий бонус: chrome-devtools-mcp уже виставляє `list_webmcp_tools`/`execute_webmcp_tool`, а WebMCP (`document.modelContext`) з Chrome 146 доступний у ранньому прев'ю, тож підтримка структурованих інструментів сайту у шарі спостереження — реальний диференціатор ([tool-reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [Chrome WebMCP blog](https://developer.chrome.com/blog/webmcp-epp)).

Шар дій має бути гібридним: читання через content script (`chrome.scripting.executeScript` з `allFrames: true`), а ввід — через `chrome.debugger` і CDP `Input.*`, бо лише так події мають `isTrusted = true` і задовольняють вимоги user activation; синтетичні `dispatchEvent` із content script не проходять на фреймворках, що перевіряють `isTrusted`. Nanobrowser використовує для цього puppeteer-core `ExtensionTransport.connectTab`, який у документації Puppeteer досі «experimental», обмежений однією сторінкою на з'єднання і не вміє створювати нові вкладки ([pptr.dev](https://pptr.dev/guides/running-puppeteer-in-extensions)); тонка власноруч написана обгортка над `chrome.debugger` (як у mcp-chrome і Playwright Bridge) — легша альтернатива без «internal»-імпортів. Сесія `chrome.debugger.attach({tabId}, "1.3")` має одразу вмикати `Page`, `Runtime`, обробляти `Page.javascriptDialogOpening` (інакше сторінка блокується і всі подальші CDP-виклики зависають), використовувати `Page.setInterceptFileChooserDialog` + `DOM.setFileInputFiles` для завантажень, а для cross-origin iframes — `Target.setAutoAttach({flatten: true})` з маршрутизацією через `sessionId` (Chrome 125+) ([CDP Page](https://chromedevtools.github.io/devtools-protocol/tot/Page/), [chrome.debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger)).

## Ollama тягне задачу лише від 27B і з контекстом 32–64K

Легкі локальні моделі для такої агентики використовувати можна, але очікування треба калібрувати. Самостійні тести Browser Use + Ollama дають чітку драбину: `llama3.1:8b` (4,9 GB) працює для відкриття сайту і читання одного елемента, «часто працює» на простих формах і «здебільшого провалює» багатокроковий пошук/порівняння і будь-які логіни з попапами; `qwen2.5:14b` (9 GB) дає «помітно стабільніший» вивід дій; `qwen3-vl:30b` (20 GB, 24 GB VRAM) — рівень, де «vision + надійність починають відчуватися реальними», але й там багатокроковість «hit and miss», а задача, яку людина робить за 40 с, у локальної 30B-моделі займає кілька хвилин ([localaimaster](https://localaimaster.com/blog/browser-use-ollama-local)). Рекомендації самих фреймворків збігаються: Nanobrowser радить для Ollama Qwen3-30B-A3B-Instruct-2507, Falcon3 10B, Qwen 2.5 Coder 14B і Mistral Small 24B, попереджаючи, що «local models require more specific and cleaner prompts» ([Nanobrowser](https://github.com/nanobrowser/nanobrowser)); BrowserOS стартує з `qwen3-4b` для 8 GB RAM, Magistral Small/Devstral для 16 GB+ і gpt-oss 120B для 64 GB+ ([BrowserOS local models](https://docs.browseros.com/features/local-models)). Відсоток добре сформованих tool calls на Q4_K_M — Gemma 4 27B ~95%, GLM-4.7 32B ~94%, Qwen3 32B ~93%, Qwen3-Coder 30B ~96% — виглядає обнадійливо, але це необхідна, а не достатня умова: помилка на крок множиться на 10–30 кроків браузерної задачі ([promptquorum](https://www.promptquorum.com/power-local-llm/best-local-models-tool-calling-2026)). Єдині малі відкриті моделі з опублікованими web-agent бенчмарками — спеціалізовані GUI-VLM: UI-TARS-1.5-7B з 84,8 на WebVoyager і Holo2-8B (Apache 2.0) з 80,2 WebVoyager / 42,2 WebArena, проте вони видають координатні дії по скриншоту і потребують іншого harness, ніж індексне DOM-дерево ([UI-TARS-1.5-7B](https://huggingface.co/ByteDance-Seed/UI-TARS-1.5-7B), [Holo2-8B](https://huggingface.co/Hcompany/Holo2-8B)).

Контекст — найчастіша причина поломок. Ollama виставляє за замовчуванням **4K токенів при VRAM < 24 GB**, 32K при 24–48 GB і 256K від 48 GB, і сам рекомендує для «web search, agents, and coding tools» щонайменше 64 000 токенів (`OLLAMA_CONTEXT_LENGTH=64000 ollama serve` або `num_ctx` на запит) ([Ollama docs](https://docs.ollama.com/context-length)). Оскільки a11y-снапшот коштує до 5K токенів і накопичується з кожним кроком (Playwright MCP ≈ 114K токенів на задачу проти ≈ 27K для CLI-обгортки), 4K-контекст переповнюється вже на першій сторінці, а при 16K — після ~4 кроків, після чого модель зациклюється або видає сфабриковані індекси елементів; BrowserOS прямо пише, що 4 096 за замовчуванням «causes the agent to loop» ([morphllm](https://morphllm.com/playwright-mcp), [BrowserOS](https://docs.browseros.com/features/local-models)). Квантування теж має пастки: Q4_K_M — «production minimum», але INT4 KV-cache у 100k-токеновому тесті Qwen3.6-27B давав невідновлювані збої tool calls, NVFP4 — ~50% перекручених токенів до 88k, а AWQ W4A16 «не закривав tool calls коректно» ([mer.vin](https://mer.vin/news/local-llm-quantization-benchmarks-reveal-silent-tool-call-failures/?amp=1)). Великі vision-моделі (24–35B) через Ollama вибивали 60-секундний таймаут кроку Browser Use, що вилилося в issue #5017 ([browser-use #5017](https://github.com/browser-use/browser-use/issues/5017)).

Кому з шести агентів можна підсунути Ollama — питання не менш важливе. **Claude Code** працює через нативний Anthropic-сумісний API Ollama з v0.14.0 (`ANTHROPIC_AUTH_TOKEN=ollama`, `ANTHROPIC_BASE_URL=http://localhost:11434`, `claude --model gpt-oss:20b` або `qwen3-coder`), але без `tool_choice`, prompt caching і token counting, що робить повторні великі снапшоти дорожчими за латентністю ([Ollama blog](https://ollama.com/blog/claude), [Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility)); практичні тести називають GLM-4.7-Flash і Devstral-Small-2 «надійними для агентних сценаріїв» при 32K мінімум і 128K бажано ([KDnuggets](https://www.kdnuggets.com/pairing-claude-code-with-local-models)). **Codex CLI** має `codex --oss` з `gpt-oss:20b` за замовчуванням, **OpenCode** — офіційну інтеграцію з `ollama launch opencode` і вимогою контексту 64k+ ([Ollama OpenCode docs](https://docs.ollama.com/integrations/opencode)). Натомість **Gemini CLI** підтримує лише експериментальне локальне роутування на Gemma-1b через LiteRT-LM, а не повноцінну локальну модель, а **Cursor** проксіює всі запити через свою хмару, тож Ollama потрібен публічний тунель і він працює лише для Chat/Cmd+K ([Gemini local routing](https://geminicli.com/docs/core/local-model-routing), [Cursor forum](https://forum.cursor.com/t/support-for-ollama-provided-local-models/156792)). Практичний стек на 16–24 GB GPU: Qwen3-30B-A3B або Qwen3-Coder-30B-A3B на Q4_K_M, `num_ctx` 32–64K, ≤6 інструментів, JSON-schema-обмежений вивід, обрізання старих снапшотів на кожному кроці, temperature ≤0,3 — і готовність до успішності помітно нижчої за хмарні моделі. Альтернатива без ключів для дешевих підзадач — вбудований у Chrome Prompt API (Gemini Nano, `LanguageModel`), який у розширеннях стабільний у релізному Chrome і годиться для класифікації ризику дії чи підсумовування сторінки ([Chrome Prompt API](https://developer.chrome.com/docs/ai/prompt-api)).

## Платформа Chrome і prompt injection ламають агента частіше, ніж модель

Першою платформною пасткою є життєвий цикл MV3 service worker: він гине після **30 с бездіяльності** або коли одна подія триває понад 5 хв. Таймер скидають виклики extension API, повідомлення long-lived портів (Chrome 114+), WebSocket-повідомлення (116+), offscreen-документи (109+), а структурно живим worker тримають `runtime.connectNative()` (105+) і активна сесія `chrome.debugger` (118+); `chrome.alarms` мінімум 30 с від Chrome 120 ([SW lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)). Навіть Anthropic визнає, що «the Chrome extension's service worker can go idle during extended sessions, which breaks the connection», пропонуючи кнопку «Reconnect extension» ([Claude Code docs](https://code.claude.com/docs/en/chrome)). Практичний висновок: під час задачі keepalive дає сама debugger-сесія, між задачами — native-порт або offscreen-heartbeat за зразком mcp-chrome, стан — у `chrome.storage.session`, а не в глобальних змінних.

Друга пастка — сам `chrome.debugger`. Він показує жовтий банер «<ext> started debugging this browser», який у брендованому Chrome прибирається лише прапорцем `--silent-debugger-extension-api` або force-install через enterprise-політику `ExtensionInstallForcelist`; запит на офіційне приховування Anthropic закрито як «not planned» ([Claude issue #69287](https://claudeissues.com/issue/69287-claude-in-chrome-started-debugging-this-browser-banner-shows-on-every-tab-please), [UiPath](https://docs.uipath.com/studio-web/automation-cloud/latest/user-guide/debugging-banner-notification-after-extension-upgrade-to-manifest-v3)). До target може бути прикріплений лише один дебагер: відкритий DevTools блокує `attach()` або від'єднує з причиною `canceled_by_user`, тому розширенню краще показати «закрийте DevTools», ніж перепідключатися в циклі ([chrome.debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger)). Chrome 155 (стабільний з 2026-10-06) додав відмови за політикою — «Host access is restricted by policy» при `runtime_blocked_hosts` і «Screenshot capture is restricted by policy» під DLP, тож корпоративні установки можуть повністю заблокувати debugger-агента і content-script fallback для читання стає обов'язковим ([Chrome blog](https://developer.chrome.com/blog/debugger-enterprise-policy-restrictions)). Доступні CDP-домени обмежені 24-ма, а `sidePanel.open()` викликається лише у відповідь на дію користувача, тому host не може «відкрити» панель сам — потрібен `openPanelOnActionClick` або гаряча клавіша ([chrome.sidePanel](https://developer.chrome.com/docs/extensions/reference/api/sidePanel)). Діалоги `alert/confirm/prompt` блокують усі події сторінки, і агент стоїть, доки їх не закриють, — ще один аргумент за негайну обробку `Page.javascriptDialogOpening`.

Третя й найнебезпечніша пастка — indirect prompt injection. У 2025 році впали всі комерційні агентні браузери: Comet виконав команди з коментаря на Reddit і злив OTP із Gmail лише за запитом «Summarize this page», бо «feeds a part of the webpage directly to its LLM without distinguishing between the user's instructions and untrusted content»; у жовтні Brave показала невидимий для людини текст на зображеннях, який модель розпізнавала як інструкції, а Atlas від OpenAI трактував некоректний `https://`-рядок в omnibox як промпт з довірою користувача ([Brave: Comet](https://brave.com/blog/comet-prompt-injection/), [Brave: unseeable injections](https://brave.com/blog/unseeable-prompt-injections/), [TechSpot](https://www.techspot.com/news/110049-openai-chatgpt-atlas-vulnerable-prompt-injection-attacks-within.html)). Red-team Anthropic на 123 випадках показав успішність атак **23,6% без мітигацій → 11,2% після**, а на браузер-специфічному наборі (приховані поля форм, інструкції в URL і заголовках вкладок) 35,7% → 0% завдяки per-site дозволам, підтвердженням перед публікацією/покупкою/передачею персональних даних, забороненим категоріям сайтів і класифікаторам на вході та на кожній дії ([Claude for Chrome](https://claude.com/blog/claude-for-chrome)). Для локальних моделей проблема гостріша: малі моделі мають агрегатну ефективність атак 4,2% проти 0,6–1,2% у середніх, великих і закритих, а fuzzing браузерних агентів показав найвищі показники успіху атак на функціях підсумовування (73%) і QA (71%) ([arXiv 2604.27202](https://arxiv.org/pdf/2604.27202), [arXiv 2510.13543](https://arxiv.org/html/2510.13543v1)). Playwright MCP чесно пише, що він «is not a security boundary» ([README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)). Звідси архітектурний імператив: політику має тримати host, а не модель — allowlist сайтів перед кожним observe/act, снапшот передається агенту як явно марковані дані, незворотні дієслова (send, submit, purchase, delete, publish, download, auth) гейтяться правилами плюс підтвердженням у панелі, а вільний текст моделі ніколи не стає URL без валідації. Нарешті, Chrome Web Store: `debugger` і `nativeMessaging` разом із `<all_urls>` гарантовано ведуть до ручної перевірки, тож потрібні письмові обґрунтування кожного дозволу, `optional_host_permissions` із запитом при першому використанні сайту і політика приватності ([CWS permissions policy](https://developer.chrome.com/docs/webstore/program-policies/permissions)).

## Висновок

Найважливіший зсув у 2026 році — протокольний: ACP перетворив «який агент підтримати» з продуктового рішення на конфігураційний параметр, а `session/new.mcpServers` разом із `session/request_permission` дають рівно ті два гачки, які потрібні бічній панелі — інжекцію інструментів браузера і діалог підтвердження. Тому цінність форку chrome-acp не в його коді (він невеликий), а в тому, що він довів життєздатність ланцюжка; реальна інженерна робота лежить у двох місцях, які ніхто з відкритих проєктів не закриває повністю: шар спостереження/дії з версіонованими refs, гібридом content script + CDP і обробкою iframes/діалогів, та host-шар політики, що відтворює модель Claude in Chrome (per-site allowlist, pause-on-risk, session tab group) у відкритому вигляді.

Локальні моделі варто розглядати не як заміну хмари, а як окремий режим з власними обмеженнями: 30B-A3B-клас на 24 GB із 32–64K контекстом і стиснутими снапшотами справляється з простими задачами на знайомих сайтах, тоді як вища вразливість до injection саме у малих моделей означає, що host-політика для локального режиму має бути жорсткішою, а не м'якшою. Найбільша невизначеність на горизонті — ACP v2 (зміни у форматі дозволів і diff) і подальше закручування `chrome.debugger` через enterprise-політики; будувати слід на SDK 1.0 з абстрагованим шаром дій, щоб обидві зміни лишилися локальними.
